# 2026-09-11

## VoWiFi: ICMPv6 inner packets rejected (DITO Philippines ePDG)

Symptom (app log, repeated every 1/2/4 s after `ImsRegistering`):
`[ERROR] [VoWiFi] Inner packet rejected: Unsupported inner IPv6 next-header 58; expected UDP.`

Cause: the user-space ePDG tunnel (`VoWifiManager` ESP dispatch loop) treated every inner packet as
SIP/RTP UDP. Next-header 58 is ICMPv6 — the ePDG pinging the assigned IPv6 address. A kernel tunnel
answers that in the host IPv6 stack; this one has to answer itself, and silence makes the ePDG treat
the UE as unreachable.

Work done (voSharp/src/VoSharp.Telephony/VoWifi/):
- `IpPacketUtils.TryFindIpv6UpperLayer` — walks the RFC 8200 extension-header chain so options,
  fragment and AH headers no longer masquerade as an "unsupported" protocol.
- `TryGetInnerTransport` / `IsUdpInnerPacket` — resolve the real upper-layer protocol for v4 and v6.
- `ParseIpv6UdpPacket` and `TryBuildIcmpv6EchoReply` now use that walk instead of the raw `packet[6]`.
- `VoWifiManager`: answers ICMPv6 echo requests (ESP next-header 41), and consumes any other
  non-UDP inner traffic with a once-per-protocol INFO line instead of an ERROR per packet
  (`NoteIgnoredInnerProtocol`).

## IPv6 SIP/SDP faults found while auditing the dual-stack path

DITO assigns an IPv6 address, so every SIP host:port built from the assigned IP had to be audited.
`Contact` had already been patched with `ImsRegisterBuilder.FormatHost`; `Via`, `From` and SDP had
not. An unbracketed `SIP/2.0/UDP 2001:db8::1:5060` parses as host `2001` + garbage port (RFC 3261
§25.1), and `c=IN IP4 <v6>` breaks the offer (RFC 4566 §8.2.6).

- `voSharp/src/VoSharp.Telephony/VoWifi/VoWifiManager.cs`: OPTIONS `Via` now bracketed.
- `voSharp/src/VoSharp.Telephony/Calls/ImsCallManager.cs`: INVITE `Via`, BYE `Via`+`From`, CANCEL
  fallback `Via`+`From` now bracketed; new `SdpAddressFamily` picks `IN IP6`/`IN IP4` for both the
  offer and the 200 OK answer; answer parser regex `c=IN IP[46]`.
- `voSharp/src/VoSharp.Sip/ImsRegisterBuilder.cs`: `FormatHost` is null-safe and documented.

## ADB: "more than one device/emulator" breaks the QDC507 voice runtime

`VoWin/Services/Qdc507VoiceRuntime.cs` ran bare `adb shell ...`. With a phone/emulator attached adb
refuses every command. Added `ResolveAdbSerialAsync`: honours `ANDROID_SERIAL`, otherwise parses
`adb devices`, drops emulators, and when several remain probes `uname -r` for the 3.18.44 QDC507
kernel. Every command now runs with `-s <serial>`; the cache is dropped on "device not found".

## IMS registration stage (audit vs. mdd-sim-gateway)

- **P-CSCF address-family mismatch (main suspect).** `BuildConfigurationRequest` asks for the IPv4
  *and* IPv6 P-CSCF attributes (1,3,20,8,10,21) in the default mode, so a CFG_REPLY can carry both.
  `IkeSession` took `pcscfList.FirstOrDefault()` regardless of family; with an IPv6 PDN that picks
  the IPv4 P-CSCF and every REGISTER then dies in `IpPacketUtils.BuildUdpPacket` with "Source and
  destination must use the same IPv4/IPv6 family" before it reaches the wire.
  Added `IkeSession.PickPcscf` (prefer the family of the assigned address) and
  `IkeSession.IsUsablePdn`; `CSharpIkeBackend`'s Ipv6→Dual→Ipv4 ladder now treats a mismatched pair
  as that family's failure and keeps searching (the reference's "keep the family that yields a
  usable PDN" rule). `VoWifiManager` raises an explicit error if it still mismatches.
- **P-Access-Network-Info placeholder.** Sent `i-wlan-node-id=000000000000`; the reference calls out
  constant/all-zero node ids as something P-CSCFs reject. Now derives a stable locally administered
  unicast BSSID from the SIM identity (`ImsRegisterBuilder.BuildAccessNetworkInfo`).
- **Inbound IMS IPsec SPIs.** `ImsIpsecTransport` only accepted our own SPIs; RFC 3329 §2.3.2 lets
  the P-CSCF answer with its own pair. It now accepts both, so a protected response is not dropped
  as "Unknown IMS inbound SPI".

### Open question (needs a capture, NOT changed)

`ImsIpsecTransport.Activate` assigns `_clientOutbound = PcscfServerSpi` and
`_serverOutbound = PcscfClientSpi`, and `VoWifiManager` sets the protected remote endpoint to
`agreement.PcscfServerPort`. That contradicts the class's own doc comment ("SpiClient: SA the UE
uses when sending"). Which SPI/port belongs to which direction genuinely varies between P-CSCFs, so
changing it blind could break a working carrier. Settle it from a real Security-Server/ESP capture
(DITO) before touching it.
